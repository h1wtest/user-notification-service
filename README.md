# Profile, notification, worker and admin/audit

One Go module builds four independent HTTPS processes; there is no combined application or local JWT validation. Go 1.26.10 is the pinned minimum build/CI toolchain, including standard-library security fixes. The sibling `platform-contracts` module supplies the actual validated JSON event DTOs.

| Command | Default port | Database owner | Kafka group |
| --- | --- | --- | --- |
| `go run ./cmd/profile` | 8002 | profile_db | profile-v1 |
| `go run ./cmd/notification` | 8003 | notification_db | notification-v1 |
| `go run ./cmd/worker` | 8005 | notification_db | none |
| `go run ./cmd/admin` | 8004 | audit_db | audit-v1 |

Build from the workspace root: `docker build -f user-notification-service/Dockerfile --build-arg TARGET=profile -t platform-profile:local .`; repeat TARGET `notification`, `worker`, `admin`. Docker ignores all unrelated workspace content and secrets. No build-time `go mod tidy` or remote publication occurs.

## Migrations and ownership

For each owner run its command with the single `migrate` argument and DATABASE_URL using that owner's migration credential, before starting runtime deployments:

```sh
go run ./cmd/profile migrate
go run ./cmd/notification migrate
go run ./cmd/admin migrate
```

`worker migrate` applies notification's identical migration. SQL is compiled into `internal/platform/migrate.go`; version 1 is applied transactionally under a PostgreSQL advisory lock. `service_schema` records owner/version, and another owner's marked database is rejected. Readiness requires this marker; runtime does not auto-migrate. Existing unrelated database rows/tables are not dropped. A migration role needs CREATE on its own database/public schema; runtime needs SELECT/INSERT/UPDATE/DELETE on that owner's tables and USAGE/SELECT on its sequences. `ALTER DEFAULT PRIVILEGES FOR ROLE <migration-role> IN SCHEMA public GRANT ...` must be configured by bootstrap. Runtime roles must not own databases or have CREATE, and must not have access to other databases.

All owners have transactional inbox, encrypted quarantine and DLQ outbox. Profile additionally owns profiles/settings/Telegram bindings. Notification owns delivery jobs/attempts/replay audit; worker shares precisely this DB. Admin owns audit projections/command audit only and never queries identity/profile/notification tables.

When upgrading persisted ciphertext from the former universal key, do not replace it with unrelated keys at startup. Stop the owner's API/consumer/worker deployments, apply owner migrations, then run its command with `rekey` using migration DATABASE_URL, LEGACY_ENCRYPTION_KEY, new QUARANTINE_ENCRYPTION_KEY and (notification owner only) new DELIVERY_ENCRYPTION_KEY. The command re-encrypts quarantine originals with topic:partition:offset AAD, quarantine_replays corrections with quarantine UUID AAD, and nonempty delivery job bodies with job UUID AAD. One owner transaction/advisory lock covers rows plus service_key_migrations fingerprint marker; any wrong key/error rolls back everything. Repeating the same target fingerprints is a no-op; different target fingerprints fail closed. Do not restart runtimes or remove the legacy key until every owner and identity migration succeeds. Failed delivery bodies remain recoverable; no data is deleted. Runtime never accepts the legacy key as fallback.
Notification quarantine/correction rekey also authenticates a nested sensitive command envelope, validates its canonical decrypted payload and aggregate identity, re-encrypts encrypted_payload under the delivery-purpose key with unchanged event_id AAD, then encrypts the outer record under the owner quarantine key. A malformed sensitive envelope, wrong nested GCM tag or invalid inner payload aborts the entire owner transaction and leaves marker/ciphertexts unchanged. Plain malformed poison bytes without a parseable sensitive envelope remain preserved as poison, never silently repaired.

## Required environment

See `.env.example`. DATABASE_URL is per process, with `sslmode=verify-full` and CNPG CA `sslrootcert` mounted by infrastructure. DELIVERY_ENCRYPTION_KEY is standard-base64 32 random bytes shared only by identity's delivery publisher and notification/worker (AES-256-GCM, nonce12+ciphertext+tag, event_id AAD). Profile/admin never receive it or identity's separate MFA_ENCRYPTION_KEY. QUARANTINE_ENCRYPTION_KEY is a different random key for each DB owner. Preserve keys across restarts and encrypted backups; rotate through an explicit re-encryption migration. Jobs use their own job ID as AAD when re-encrypted locally. No universal ENCRYPTION_KEY alias is accepted. Kafka requires CA-verified TLS plus SCRAM-SHA256 via KAFKA_TLS_CA_FILE/KAFKA_SASL_USERNAME/KAFKA_SASL_PASSWORD; ACLs restrict profile/audit to public events and notification alone to commands, with distinct group IDs and metadata-only DLQ write. No verification/reset code is written to audit/history/logs; successful jobs erase encrypted message bodies.

HTTPS listener: TLS_CERT_FILE/TLS_KEY_FILE; internal trust: INTERNAL_CA_FILE. Every process has its own INTERNAL_SERVICE_TOKEN. Identity knows PROFILE_INTERNAL_TOKEN/NOTIFICATION_INTERNAL_TOKEN/ADMIN_INTERNAL_TOKEN. Profile also receives NOTIFICATION_INTERNAL_TOKEN for read-only notification settings; notification receives ADMIN_INTERNAL_TOKEN for delivery operations. No shared privileged service secret. Internal URL variables are IDENTITY_URL, PROFILE_URL, NOTIFICATION_URL; default HTTPS service DNS and ports match the table.

Every protected browser request forwards cookie/bearer plus CSRF/Origin to identity introspection with a five-second deadline. No caller-supplied user ID can select another user's profile/history. Admin additionally requires current MFA and users:read/users:write/audit:read/deliveries:read/deliveries:replay. Internal notification admin routes independently recheck actor authorization. Ban/unban goes through identity's internal API, not SQL. Audit records command requested/succeeded/denied/unknown, including ambiguous dependency outcomes.

`PATCH /api/v1/users/me` treats `display_name`, `avatar_url` and `phone_number` independently: an omitted field retains its stored value, JSON `null` stores SQL NULL, and `""` stores an empty string. Non-null values retain the existing 100-byte display-name, 30-byte phone-number and 2048-byte HTTPS-avatar limits (empty avatars remain allowed). Unknown fields and non-string/non-null field values return 400. In Go, `NullableString{Present: true, Value: &value}` replaces a field, `NullableString{Present: true}` clears it, and the zero value leaves it unchanged.

`GET /health/live`, `/health/ready`, `/metrics` are TLS endpoints; metrics must not be exposed by the public gateway. Schema absence produces 503 readiness. Consumer readiness also checks Kafka. Notification worker readiness requires its schema/database, not provider uptime: provider failure is durable retry, not crash-loop policy. OTEL_EXPORTER_OTLP_ENDPOINT enables bounded, nonblocking OTLP/HTTP span export; W3C traceparent is forwarded HTTP to Kafka to jobs. Telemetry export does not block business work.

## Events and delivery

Topics identity.events.v1 and notification.commands.v1 use validated canonical DTOs. Sensitive command envelopes are encrypted top-level encrypted_payload and never public audit payload. Kafka auto-commit is disabled. A record is committed only after inbox+projection/jobs transaction or durable encrypted quarantine transaction. Dependency failures retry the same record without advancing its partition offset; settings projection lag therefore cannot drop a notification. No SMTP/Telegram call runs in the consumer. A DLQ outbox publishes metadata-only platform.dlq.v1 notices; encrypted originals remain in the owning DB.

Worker claims with SKIP LOCKED, a 60-second lease token, 15-second provider deadline, persisted attempts and jittered exponential backoff. Up to eight attempts, then failed; permanent errors fail immediately. Stable Message-ID survives retries/replay. The unavoidable provider-accepted/local-commit crash window can produce duplicates: recovered leases and unknown network outcomes record ambiguous=true. SMTP is at-least-once, not exactly-once. SMTP_ALLOW_INSECURE=true is allowed only for explicit local Mailpit; otherwise STARTTLS is mandatory. SMTP_USER/SMTP_PASSWORD configure optional provider authentication.

Public history lists only metadata. Failed jobs can be replayed through POST /api/v1/admin/deliveries/{id}/replay with live MFA permission; active/sent jobs cannot be replayed. GET /api/v1/admin/quarantine and POST /api/v1/admin/quarantine/{id}/replay accept `?owner=notification` (default), `profile`, or `audit`; the owning API validates actor authorization and only accesses its own database. POST `{}` revalidates the original; still-invalid bytes return 409 and remain quarantined. An authorized operator may POST `{ "corrected_event": <complete canonical envelope> }`; strict version/type/payload/aggregate/topic validation runs again. Parseable original event_id/aggregate_id cannot be changed (409 record_identity_mismatch); malformed original JSON permits a new canonical identity. The original remains immutable and encrypted, and quarantine_replays records actor and encrypted correction before application, then completion after successful inbox transaction. Repeated application is inbox-idempotent after a crash. The admin service separately records its downstream command outcome. Quarantine responses never expose original/corrected bytes or delivery secrets.

## Telegram external acceptance gate

Without both TELEGRAM_BOT_TOKEN and TELEGRAM_WEBHOOK_SECRET, capability is false and link creation returns 503. With real credentials, POST /api/v1/users/me/telegram/link performs real getMe and creates a ten-minute, hashed, one-use token and deep link. Configure the real Bot API setWebhook to an externally reachable HTTPS URL ending `/internal/v1/telegram/webhook`, with secret_token equal to TELEGRAM_WEBHOOK_SECRET. Only that exact webhook route may be exposed by the gateway; all other internal routes stay private. Telegram delivers a secret-authenticated private-chat `/start <token>` update; the transaction consumes the link, records update deduplication and binds that chat uniquely. Arbitrary PATCH telegram_id is rejected. Refresh GET /api/v1/users/me to observe verified telegram_id before enabling Telegram preferences. Worker uses real sendMessage, checks HTTP/JSON success and classifies failures. Never send internal service tokens to Telegram.

Real bot credentials, externally reachable callback and user-controlled test chat were not provided. Genuine Telegram acceptance remains external and must not be represented as passed by local protocol tests.

## Verification commands (not executed by implementation worker)

After all repository changes land, integration owner runs `gofmt -w cmd internal`, `go mod download`, `go vet ./...`, `go test -race ./...`, `go build ./cmd/...`, and image builds for all TARGETs. TEST_DATABASE_URL must name a disposable test database; PostgreSQL duplicate/retry/quarantine regressions skip explicitly when absent. Profile PATCH regressions create and remove their own uniquely named profile-owner schema within that database, so the test credential also requires CREATE SCHEMA permission; no separate profile database or production access is required. Run the focused profile regressions with `go test -race ./internal/profile -run 'TestProfile(Patch|Policy)' -count=1`. TLS authorization/header validation/cipher/real local SMTP rejection tests run without a database. CI provisions an isolated PostgreSQL DB and runs these checks; CI files do not prove any checks have already executed. Full real API/SMTP/Kafka, persistence, poison/replay, failed-provider recovery and browser acceptance are owned by platform integration, not by a competing service harness.
CI uses digest-pinned PostgreSQL 18.6 and `bash scripts/ci-broker.sh`, which starts a unique disposable digest-pinned Redpanda 26.2.5 container, waits for genuine broker readiness, creates the three exact topics and runs the full race suite with TEST_KAFKA_BROKERS set. Plaintext Kafka is loopback-bound and test-only; runtime TLS/SCRAM requirements are unchanged. The EXIT trap removes only the uniquely named test container. Gitleaks 8.30.1 is digest-pinned and scans complete service Git history plus the pinned contracts tree before installing dependencies; output is redacted and reports are not uploaded. Checkout credentials are not persisted. Contracts must be published first, with the approved immutable SHA supplied through `PLATFORM_CONTRACTS_REVISION` before service branch publication; CI verifies the actual checkout and recorded contract-tree digest and records both source revisions. Initial push/PR checks run before manual dispatch is available on `main`.

CI builds each final profile/notification/worker/admin scratch image with immutable service/contract revisions and the verified contracts-tree digest in its labels and tag, without publication. Vulnerability scanning and scanner-only image exports/report cleanup are disabled by policy. Secret scans, provenance checks, tests and builds remain required, and existing patched dependencies/images remain pinned. Removing vulnerability gates does not establish an absence of vulnerabilities.

## Remediation change record

Replaced obsolete combined app, HS256-only authentication, wildcard CORS, synchronous Kafka SMTP and nontransactional processed-event writes with separate owner processes, authoritative introspection, transactional inbox/jobs, encrypted delivery/quarantine and protected admin APIs. Migrations, build targets and CI now name actual runtime commands. No cloud operations or repository publication are part of this change.

Security review corrections: absent credential headers remain absent; explicit empty/invalid authorization fails closed instead of cookie fallback. Kafka mixed-partition failures no longer discard healthy records, retries have bounded processing/commit deadlines, failed offsets are reseeked under blocked ownership before AllowRebalance. Lag decreases only after durable success and broker commit. Shutdown joins consumer/DLQ or worker before closing the pool; SMTP sockets close on cancellation. An expired eighth lease becomes failed/ambiguous without a ninth send. Persistent delivery_attempts rows provide `delivery_attempts_total{status}` independent of replay resetting job attempts. Maintained Prometheus histograms expose actual latency buckets with registered route patterns, never raw URLs. Immutable builder digest and scratch runtime eliminate mutable apk installation. CI requires an explicit immutable contracts revision and checked-in contracts-tree.sha256, verified by scripts/contracts-digest.py; unavailable revision fails closed. Image labels bind service commit, contracts commit and source digest. Application repository interfaces own atomic profile/inbox/job/audit transitions; delivery provider ports isolate SMTP/Bot transport from application policy.
