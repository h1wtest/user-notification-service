# platformkit — owner-local technical runtime

Exports only transport, database lifecycle, migration and delivery primitives. Domain types and business SQL stay in each importing service. Exact API is the approved C02 integration contract.

## Lifecycle and migrations

Use `Load(name, defaultPort)`, `Connect`, an explicit `migrate` command calling `Migrate(ctx, db, name, steps)`, then `Serve`. Include `SchemaSQL` in the first owner migration. Versioned SQL bytes are immutable; supplied versions must be consecutive starting at one. The database has a singleton owner and SHA-256 migration ledger. Wrong owner, changed checksum, removed history, newer installed schema and legacy `service_schema` all block this fresh-owner runner. Legacy owners keep their existing internal/platform upgrade runner.

Serve executes no DDL. Empty schema stays live200/ready503/business503. Business dispatch and background startup require both the owner marker and the supplied readiness callback, which must assert the exact installed domain schema and required local runtime state. Do not put external SMTP/Telegram/payment provider availability in that callback: durable delivery must still retry through provider outages. Once started, background work continues until canceled/fails; readiness is not a worker liveness toggle. HTTPS listener and background failure cancel each other; shutdown waits with a ten-second deadline and preserves cleanup failures joined with cancellation. `/metrics` exposes readiness, pool counts, pending outbox and quarantine counts without business labels.

Business admission has a separate 250ms context deadline for owner-local schema/runtime checks; timeout returns 503 `not_ready`, never an authentication denial and never invokes the business handler. `/health/ready` retains its three-second diagnostic budget. Owner callbacks must honor context (pgx queries inherit it); database pressure may correctly fail closed. Handler-owned deadlines remain independent: a 2.5s durable callback follows at most 250ms of cooperative preflight, rather than a prior three-second probe wait. No route-specific logic or public API field is added.

## Configuration and admission

Required environment: DATABASE_URL, PUBLIC_ORIGIN (HTTPS origin), INTERNAL_SERVICE_TOKEN, TLS_CERT_FILE, TLS_KEY_FILE, INTERNAL_CA_FILE, KAFKA_BROKERS (comma-separated host:port), KAFKA_TLS_CA_FILE, KAFKA_SASL_USERNAME, KAFKA_SASL_PASSWORD. HTTP_PORT overrides the caller default. IDENTITY_URL defaults to https://identity-service:8001. Consume also requires QUARANTINE_ENCRYPTION_KEY containing base64-encoded 32 random bytes. Keep keys stable across restarts and retain retired keys for operator-controlled quarantine recovery; rotating ciphertext is an explicit owner operation, not automatic key loss.

Client calls use HTTPS, explicit service-token header, five-second deadline, one-MiB request/response limits and no redirects. Content-Type is only present when a body exists. JSON decoding rejects duplicate keys, case-insensitive aliases of typed struct members, unknown fields, null/empty/trailing bodies and over-one-MiB bodies. Exact case-sensitive arbitrary map keys remain distinct; nullable scalar semantics still come from the generated schema.

Authenticate always obtains a fresh `/internal/v2/introspect` decision with the original request method, origin, CSRF, permission and require_mfa. V2 deliberately retains the credential request shape from v1, and maps response is_verified to Actor.Verified; there is no fallback to the v1 endpoint. The authoritative identity service enforces fresh MFA, permissions, revocation, origin and CSRF. Kit also rejects inactive actors, missing permission or missing required MFA. It never caches a decision or trusts user ID/role headers.

Incoming workload authorization belongs to the owner: compare X-Service-Token constant-time against the configured narrow per-caller token before calling Authenticate on internal actor commands. Authorization Bearer is reserved for actor OAuth, never workload identity. ForwardActor copies cookie/bearer/CSRF/origin/trace headers; X-Actor-Session/Token are only adopted from internal routes with a workload header, so the owner must authenticate that header first. Public X-Actor-* headers are not trusted.

Authenticate passes the original request through ForwardActor to identity, including both `sso_session` and `sso_csrf` cookies. The introspection request body alone does not contain the double-submit CSRF cookie. Identity still compares that cookie, the CSRF header/body token and exact Origin; forwarding them preserves policy rather than bypassing it. Forged public X-Actor-* credentials are cleared and reconstructed only from canonical browser credentials.

## Event transaction contract

An owner's SQL transaction assigns a dedicated emitted-event sequence (not optimistic business version), calls Enqueue, and commits business effects plus event atomically. Use UUIDv7 event IDs; generated eventsv2.Envelope validates exact producer/type/aggregate/topic and typed body. Exact duplicate Enqueue is idempotent; conflicting IDs or aggregate versions fail. SchemaSQL has outbox/inbox/event_cursors/encrypted quarantine/metadata DLQ tables.

Run Relay with the same owner Config. It leases one eligible earliest unpublished aggregate event, publishes key=aggregate UUID with idempotent Kafka producer and all-ISR acknowledgment, then updates only its unexpired fenced lease. Broker errors persist retry state; a stale publisher cannot acknowledge a reclaimed lease. Multiple replicas never lease a later aggregate version while an earlier stored event is unacknowledged. DLQ publication follows the same lease/ack rules and contains metadata only, never source bytes. Kafka ACLs require exact topic writes plus cluster IdempotentWrite if required by the broker; no transactional IDs are used.

Bounded delivery explicitly enables franz AllowIdempotentProduceCancellation: otherwise default idempotency can wait indefinitely for an uncertain broker write despite the attempt context. Internal retries retain idempotent deduplication, but application retries after cancellation can duplicate an already-written record. This is honest at-least-once transport, resolved by transactional Inbox. Produce requests use a three-second broker timeout plus two-second socket overhead and a fifteen-second record/attempt deadline, bounded before the thirty-second durable lease. An ambiguous cancellation never marks published. Consumer shutdown explicitly leaves the group with a two-second deadline before closing the client.

Consume owns **inbox + callback effects + aggregate cursor** in one pgx transaction, and only then acknowledges Kafka offsets. The callback must not call Inbox again. Standalone Inbox is for transaction paths outside Consume. Duplicate committed event IDs do not invoke effects again; reusing IDs with changed content or type is poison. Dependency errors roll back and retry; only generated-invalid input or explicit ErrPoison enters encrypted quarantine plus DLQ metadata in a local transaction before offset acknowledgment.

Every stream `(producer, aggregate_type, aggregate_id)` has contiguous versions starting at one, on exactly one topic. Subscribe to whole topics; return nil for valid irrelevant event types so their inbox/cursor advances. Gaps produce observable `sequence_gap_owner_replay_or_snapshot_required` logs and do not apply later effects or classify dependency absence as poison. Recovery is an owner replay of the missing historical events before retry, or a separately authenticated/audited owner snapshot migration which seeds event_cursors consistently with restored business state. Starting after retention has removed version one requires this explicit recovery; kit never guesses state from timestamps or skips the gap. Failed records are reseeked before releasing rebalance ownership, and attempts/offset commits are bounded.

## Owner telemetry

`Serve` initializes one bounded OTLP/HTTP JSON exporter using `OTEL_EXPORTER_OTLP_ENDPOINT` and canonical `Config.Name` as `service.name`. It follows the existing `internal/platform` exporter wire pattern without importing an internal package. No endpoint means tracing export is disabled. Export requests prohibit redirects, have a three-second deadline, and carry at most 64 spans; the queue holds 256 spans and drops rather than blocking requests. `telemetry_dropped_spans_total` reports overflow. Shutdown waits at most three seconds for telemetry independently of business cleanup.

Shutdown closes recording admission, stops normal batching, and applies one deadline (the caller budget capped at three seconds) to the owned exporter lifetime. Deadline cancellation interrupts in-flight HTTP requests; shutdown joins the exporter worker rather than leaving a detached flush. Disabled export allocates no queue, and disabled/unsampled spans retain propagation without constructing OTLP timestamps, attributes, or links.

Inbound HTTP validates W3C `traceparent` and preserves its sampling decision. Server and workload-client spans propagate their active parent across TLS requests. Span names and metric route labels use registered ServeMux patterns or `unmatched`; unknown methods become `OTHER`. Telemetry never records raw request paths, query strings, credentials, bodies, event payloads, user IDs, or dependency error messages. The response includes the server span's `Traceparent`.

Technical wrappers that copy requests to add deadlines use `RequestWithContext(r, ctx)` so telemetry can observe the leaf mux's registered pattern rather than an outer `/` catch-all. The per-request holder uses an atomic pointer; normal ServeMux request ownership still requires handlers to finish before returning. Scraping snapshots metric values under the runtime mutex and releases it before formatting or HTTP writes, so a slow scrape cannot hold the business metrics lock.

`Enqueue` derives missing envelope trace metadata from its transaction context; explicit producer metadata is untouched. A same-event retry under another request context retains the original stored trace and immutable event bytes, while business-envelope or explicit-trace collisions still fail. Relay spans parent/link to that durable context and inject their producer context into Kafka headers. Consumer spans parent to the Kafka producer and link back to the durable envelope, including their offset commit outcome.

`/metrics` adds `http_requests_total`, `http_request_duration_seconds` (histogram), `outbox_oldest_pending_age_seconds`, `event_retries_total{operation,reason}`, and `kafka_sampled_committed_lag` with observation timestamps. Lag is sampled from the fetched high watermark and advances only after successful transaction plus broker commit; revoked/lost partition samples are removed. Retry reasons are fixed operational classifications, not error strings. Existing readiness, pool and pending counts remain unchanged.

## Verification handoff

No checks are run by the implementation worker. Parent runs gofmt, `go test ./platformkit`, `go test -race ./platformkit`, and go vet with pinned Go 1.26.10. Real PostgreSQL tests use TEST_DATABASE_URL and create/drop isolated test schemas. Real Kafka tests additionally use TEST_KAFKA_BROKERS, TEST_KAFKA_CA, TEST_KAFKA_USERNAME, TEST_KAFKA_PASSWORD against the disposable authenticated TLS/SCRAM broker. Runtime never has a plaintext fallback.
